# Desktop connection fragments

The implementation follows WhiteVPN Android 1.7.1 (`b1340272503b2594dd979aae1412d54265fb1524`).
Core inputs are pinned in `desktop/scripts/mihomo-pins.sh`:

- WhiteDNS/FlClash: `8f08f6e2d732c58bcbb9d13771af4456c039fe46`
- WhiteDNS/mihomo: `05fb40f89637aa27d81b638bff765a6d57797cdb`
- Go: `1.26.8`, mihomo base version: `1.19.30`

## Behaviour

Fragments are off by default, including existing installations. The VPN dashboard
opens the settings section. Six Android presets, custom FinalMask JSON, ALPN and
TLS cipher suites are persisted with WhiteVPN settings. Applying changed settings
restarts an active mihomo connection. Invalid edits are rejected before storage.
Disabling from the fragment switch retains the last saved valid configuration.

`internal/fragment` validates and formats the schema and migrates legacy
`maxSplit: 0` to 256. `internal/mihomoconf` adds ordered `fragments` stages to
TCP proxy definitions without mutating cached subscription nodes. VLESS TLS
overrides follow Android's rules; REALITY receives a valid fingerprint when the
source leaves it blank or supplies `unsafe`/`none`. Certificate verification is not disabled.

Both connection preparation and latency/speed measurement use these settings.
Raw TCP reachability tests remain TCP dial tests. Pure datagram transports
(WireGuard/WARP, Hysteria2, TUIC) keep their own obfuscation and receive no fragments.
Provider-only YAML must first be imported as inline nodes to enable fragments.
The existing direct subscription-fetch fragmentation is independent.

Startup tries the requested options, fragments without ALPN/cipher overrides,
then normal connection options, deduplicating identical attempts. Each fragment
attempt has a 90-second startup budget. Cancellation prevents further attempts.
Failed processes are stopped and TUN adapter removal is checked before retry;
cleanup failure retains the owned engine for a later cleanup attempt.
Fallback does not change the stored preference or TLS integrity checks. Logs and
the dashboard distinguish full, fragments-only and normal fallback modes.

The build uses a separate source directory and per-target `.build-id` metadata.
Packaging checks the pins even if a binary already exists. Local binary overrides
must provide the same fragment extension.

## Verification

From `desktop`:

```powershell
go test ./internal/... .
go test -v ./internal/engine -run TestRealCoreFragmentsTLSHelloAndCarriesTraffic -count=1
npm run build --prefix frontend
```

The real-core integration test uses only localhost servers, creates no TUN and
does not change system proxy settings. It captures the first TLS record at a
local HTTPS proxy and verifies that a complete HTTP response traverses it with
fragments both off and on. It skips only when no engine binary has been built.

UI smoke verification uses Chrome and disposable values generated by the Go API:

```powershell
$env:WHITEVPN_FRAGMENT_UI_FIXTURE_OUT = "$PWD/../.cache/fragment-ui-fixture.json"
go test . -run TestFragmentUIFixture -count=1
cd ..
node desktop/scripts/fragments-ui-smoke.cjs
```

The browser test checks the dashboard shortcut, toggle persistence, all six
presets, selection after navigation, validation errors without saving, resetting,
blank TLS overrides, and English/Persian layouts. It uses a mock Wails bridge;
backend validation and persistence are covered separately by Go tests. Screenshots
and the browser report are written to `.cache/fragments-ui`.

Windows core traffic and browser UI have been tested locally. Actual filtering
effectiveness and elevated TUN behaviour require testing on the target network.
